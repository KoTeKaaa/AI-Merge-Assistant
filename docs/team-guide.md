# Договор команды AI-Merge-Assistant

Актуализировано 2026-10-09. Это общий источник решений, границ ответственности и условий интеграции. Документ самодостаточен: личные планы участников для его чтения не нужны. Описанные компоненты и проверки являются планом, пока нет соответствующего кода и результатов прогонов. Старый `architecture.md` сохранён как исторический черновик.

## 1. Что команда должна показать

За один месяц пять участников готовят веб-сервис, доступный по HTTPS-ссылке любому вошедшему через GitHub. Демонстрация проводится на подготовленных публичных Python-проектах с известными зависимостями и ожидаемым поведением. Открытый вход не означает поддержку любой системы сборки или разрешение изменять чужой репозиторий.

Пользователь выбирает исходную и целевую ветки, получает Gherkin-сценарии и pytest-тесты, видит результаты запуска и покрытие, затем может выполнить мерж. Default требует описание изменений; lazy выводит ожидания из diff без описания. В обоих режимах код используется как технический контекст, а происхождение ожиданий показывается явно.

Дополнительно: загрузка требований PDF/DOCX/MD и Python-кода без GitHub, экспорт `.feature`/`.py`/ZIP, дашборд, подсветка строк, ограниченные доработки тестов. Для загрузки без базовой версии измеряется весь загруженный прикладной Python-код; мержа нет. Обработка документа более 50 страниц выполняется в фоне, не удерживая HTTP-запрос до завершения генерации.

Мерж вручную — основной режим. Автомерж включается явно после предупреждения и проходит те же проверки. Другие языки, приватные репозитории, локальные модели, векторный поиск, произвольные Dockerfile/системы сборки и Marketplace остаются за пределами первой версии. GitHub App используется уже сейчас как механизм интеграции с отдельным веб-интерфейсом.

Надпись интерфейса согласована:

> Покрытие показывает, какая доля кода выполнялась при тестировании. Высокое покрытие и успешные тесты не гарантируют отсутствие ошибок; низкое покрытие само по себе не означает наличие ошибки. Автомерж выполняется по настроенным условиям и не заменяет проверку требований человеком.

## 2. Общий стек и размещение

| Слой | Решение |
|---|---|
| Backend | Python 3.13.x, FastAPI 0.142.4, Pydantic 2.x; модульный монолит |
| Данные | PostgreSQL 17.x, SQLAlchemy 2.0.x, Alembic 1.x |
| Фоновые этапы | Celery 5.6.x + Redis 8.x; состояние прогонов хранится в PostgreSQL |
| Frontend | React 19.3.x, TypeScript 6.0.x, Vite 8.x, Node.js 24 LTS; polling |
| LLM | Gemini Developer API через google-genai 2.29.0; model ID в конфигурации |
| Проверки | pytest 9.1.1, coverage.py 7.16.2, diff-cover 10.6.0; Ruff 0.16.10 |
| Артефакты | Отдельный volume; в БД пути, размеры, хеши, принадлежность и срок хранения |
| Развёртывание | Один зарубежный VPS, Docker Compose v2, отдельные сервисные контейнеры и одноразовые sandbox под gVisor |

Точные patch-версии и совместимость пока не подтверждены сборкой. Pydantic 2.14.0 и указанные версии вспомогательных инструментов — начальные pins; владелец каждого компонента проверяет их при создании каркаса. Версии Docker Engine и `runsc`/digest образов подбирает Макс под выбранный VPS.

API, worker, БД, Redis и контроллер runner работают раздельно. Только контроллер runner имеет доступ к механизму создания sandbox; API, LLM-worker и тестируемый код не получают Docker socket. Контроллер принимает фиксированное задание, а не произвольную команду от модели или браузера.

Запуск готового пакета: `docker compose up --build`. Подготовка хоста, установка gVisor, DNS/HTTPS и заполнение внешней конфигурации предшествуют этой команде. Несколько контейнеров соответствуют требованию готового Docker-пакета; один общий контейнер не требуется.

На одном VPS остаётся общая зона отказа и риск для хоста. Изолированный интерфейс runner должен позволять позже перенести его на отдельную VM/VPS без изменения LLM-контракта. В продукт нельзя закладывать обещание абсолютной безопасности контейнеров.

## 3. Обязанности и результаты каждого участника

У каждой функции есть один основной владелец реализации; потребители согласуют её контракт. Отсутствующий соседний модуль временно заменяется fixture/fake на границе, а не второй реализацией внутри своей зоны.

| Участник | Что реализует | Что обязан передать команде | Как принимается результат |
|---|---|---|---|
| **Вадим — сначала LLM** | Gemini-адаптер, настройки, сценарии default/lazy, pytest-генерация и одна доработка по feedback, бюджеты, метаданные | Три метода генерации, DTO, безопасные ошибки, fake, локальную CI-команду, примеры и описание интеграции | Offline-тесты без сети; реальные генерации default/lazy; доработка через готовый sandbox; отчёт о качестве и лимитах |
| **Вадим — GitHub App** | Клиент GitHub, протокол авторизации, токены, чтение веток/снимков, публикация тестов/PR, проверки, GitHub-вызов мержа, проверка webhook | Сервисный интерфейс, DTO, ошибки/статусы GitHub, инструкции установки, тесты HTTP-клиента | Read/write-контракты и затем прогон на отдельном демо-репозитории; запись только с правами пользователя и действующим допуском |
| **Артём З — приложение** | HTTP API и сессии, БД/миграции, очередь и оркестратор, сохранение результатов, client runner, нормализация результатов/покрытия, допуск к мержу, статистика | OpenAPI, общие DTO, состояния/ошибки, модели, идемпотентность, вызовы LLM/runner/GitHub, защищённые маршруты | Неверный/чужой запрос отклоняется; прогон не теряется молча; покрытие правильно считается; повтор не создаёт второй PR/мерж |
| **Иван — вход, качество, выход** | Извлечение текста PDF/DOCX/MD, diff/AST-контекст, статический шлюз качества, безопасная сборка экспортов | GenerationContext, ValidationFeedback по своей проверке, артефакты `.feature`/`.py`/ZIP, fixtures ошибок | Требования и код сопоставляются без исполнения; невалидные/опасные пути отклоняются; экспорт содержит проверенный набор файлов |
| **Артём Х — интерфейс** | React/TS, вход/установка App, выбор репозитория/веток, описание/lazy, загрузки, прогресс, результаты, покрытие, экспорт, дашборд, ручной/автомерж | Экраны со всеми состояниями и работой против согласованного API, frontend-тесты | Пользователь видит ошибки/лимиты/устаревший результат; N/A не показано как 100%; кнопки следуют серверному решению |
| **Макс — инфраструктура и sandbox** | VPS, Compose, HTTPS, секреты, общий CI/CD, контроллер runner и образы, ограничения и очистка sandbox | Runner-протокол, подготовленные профили, сырые отчёты pytest/coverage, health/readiness, инструкция запуска/восстановления | Чужой код не получает сеть/секреты/socket; зависший job ограничивается; контейнеры/файлы очищаются; сервис запускается по инструкции |

### Стыки, где нельзя оставлять двух неопределённых владельцев

- **Цикл генерации:** Артём З вызывает этапы и решает, нужен ли следующий. Вадим выполняет один LLM-этап и возвращает результат/ошибку. У LLM-модуля нет своей очереди, БД и второго оркестратора.
- **Валидация:** Вадим проверяет схему ответа API; Иван — допустимость артефактов и статические правила; сбор pytest и любое исполнение выполняет только sandbox Макса.
- **Покрытие:** Макс собирает исходные отчёты; Артём З нормализует пути, сопоставляет строки с diff, вычисляет числитель/знаменатель и сохраняет итог. Модель и frontend процент не определяют.
- **GitHub-вход:** Вадим реализует обмен с GitHub/получение identity; Артём З — HTTP callback, одноразовый state, сессии, cookie, CSRF и хранение токенов. Артём Х делает экран/редиректы, Макс настраивает публичные URL и секреты.
- **Мерж:** Артём З выдаёт серверное решение и защищает повтор операции; Вадим повторно проверяет актуальные GitHub-условия и выполняет API-вызов; frontend только выражает намерение пользователя.
- **Webhook:** Вадим проверяет подпись исходного тела и преобразует поддерживаемое событие; Артём З принимает HTTP, сохраняет delivery ID и ставит идемпотентную обработку в очередь. Payload с неверной подписью не вызывает изменений.
- **GitHub App:** Вадим отвечает за регистрацию/permissions и документацию установки; Макс размещает ключи/callback/webhook URL. Миграции и запись токенов/установок в БД принадлежат Артёму З.
- **Общий CI:** участники передают локальные проверочные команды; workflow, матрицу окружений и Docker-сборку собирает Макс. Изменения OpenAPI/общих DTO ведёт Артём З с потребителем.

## 4. Контракты между модулями

Названия ниже и точные поля — **ASSUMPTION T1**, начальный контракт для согласования владельцев, а не уже существующий API. Версию схемы передавать явно; примеры успеха и каждой существенной ошибки нужны до соединения модулей.

| Контракт | Производитель → потребитель | Обязательная информация |
|---|---|---|
| `SourceSnapshot` | GitHub-модуль/вход загрузки → парсер, оркестратор, runner | Вид источника, run/snapshot ID, repo ID и source/target SHA для GitHub, diff, зафиксированное содержимое/ссылка на артефакт, хеш и профиль окружения |
| `GenerationContext` | Иван + оркестратор → Вадим LLM | Снимок, default/lazy, описание/требования, diff при наличии, подготовленные фрагменты и существующие тесты, ID источников, разрешённые пути, профиль зависимостей |
| `ScenarioSet` / `TestBundle` | Вадим LLM → шлюз, оркестратор, экспорт | Сценарии со ссылками на источники и requirements/inferred; пути/текст тестов, связь со сценариями, хеш набора, модель/версия промпта, usage либо unknown |
| `RunnerJob` | Артём З → Макс | Job/run/snapshot ID, хеш набора тестов, артефакты, разрешённый профиль, лимиты, фиксированный режим collect/test; никаких секретов и произвольных команд |
| `ExecutionReport` | Макс → Артём З и шлюз | Те же ID/хеши, digest образа, статус/exit code, результаты сбора и тестов, bounded-логи, исходные отчёты покрытия, причина сбоя/таймаута |
| `ValidationFeedback` | Иван/Артём З → Вадим LLM | Идентификаторы снимка и тестов, структурированные ошибки, непокрытые изменённые строки, итерация и оставшийся бюджет |
| `MergeDecision` | Артём З → GitHub-сервис | Владелец действия, run/attempt ID, проверенные SHA/хеши, допуск или причины запрета, режим manual/auto; объект создаётся только сервером |
| `GitHubOperationResult` | Вадим GitHub → Артём З | Тип операции, repo/branch/PR, ожидаемый и фактический SHA, success/conflict/forbidden/unknown, безопасная причина, ID для сверки повтора |

Ни один DTO не переносит provider credentials в пользовательский код. Ответ LLM не считается ExecutionReport. Feedback от другого снимка или набора тестов отвергается. Unknown после сетевого обрыва записи в GitHub требует сверки фактического состояния, а не немедленного повтора записи.

Минимальная модель данных: User/Session, GitHubConnection, Installation/Repository, Run, Attempt, Scenario, Artifact, CoverageReport, GitHubAction. User владеет Run; Attempt хранит снимок и хеш тестов; CoverageReport связан с конкретной Attempt. GitHubAction хранит инициатора и ожидаемые SHA. Состояние выполнения, результат проверки и состояние мержа не смешиваются.

Предлагаемые состояния (**T1**): `queued`, `preparing`, `generating`, `validating`, `running`, `checking_coverage`, `improving`, `completed`, `failed`, `cancelled`. Отдельно: verdict `passed/failed/not_applicable`, актуальность `current/stale`, merge status. `completed` само по себе не включает кнопку мержа. Причина ошибки различает модель, окружение, тесты, квоту, права и устаревший снимок.

### API для frontend: за что отвечает Артём З

| Группа | Контракт поведения |
|---|---|
| Вход и установки GitHub App | Редирект/одноразовый state/callback, сессия, доступные установки; установка приложения и вход пользователя различаются |
| Репозитории и ветки | Только публичные поддерживаемые источники; права анализа и записи показываются отдельно |
| Создание Run | Авторизованный запрос → `202` и run ID после надёжной регистрации задания; нет ожидания LLM/runner внутри HTTP-запроса |
| Статус и результаты | Статус, этап, причина ошибки, сценарии, тесты, покрытие, актуальность и серверные причины запрета мержа |
| Upload / export / stats | Принадлежность данных, ограничения загрузок и безопасная выдача файлов/агрегатов |
| Публикация и мерж | Отдельное намерение пользователя; повтор не создаёт дубликат, stale возвращает конфликт; UI не передаёт доверенный «процент» |
| Webhook | Проверка подписи до обработки, дедупликация delivery ID, быстрый ответ и фоновые последствия |

Имена маршрутов закрепляются в OpenAPI, не копируются независимо в frontend. Для неавторизованного запроса ожидается 401, для чужой операции — согласованный отказ без утечки данных, для устаревшей версии — 409; конкретные безопасные коды ошибок входят в общую схему T1.

## 5. Неизменяемые правила покрытия и мержа

1. В GitHub-режиме измеряются добавленные и изменённые исполняемые строки Python, попадающие в результат слияния; тестовый код и неизменённые строки не входят в знаменатель.
2. Существующие и сгенерированные тесты выполняются совместно. Ошибка сбора/окружения не считается успешным тестированием.
3. Допуск: `100 * covered_changed_lines >= 90 * executable_changed_lines` при положительном знаменателе и успешных тестах. Сравниваются исходные счётчики; округление отображения не меняет решение.
4. Отсутствующий/повреждённый отчёт или неизвестный результат блокирует мерж. Изменённый измеряемый файл не может молча исчезнуть из отчёта. При нуле измеряемых строк показывается N/A, а не 100%.
5. Проверка относится к зафиксированным source/target SHA и точному набору тестов/содержимому кандидата. Новые коммиты, изменённые тесты и конфликт отменяют прежний допуск.
6. Тесты публикуются в `ai-tests/<run-id>` вместе с исходными изменениями и входят в PR к target. Запись в исходную ветку, force-push и автоматическое исправление конфликтов не входят в сценарий.
7. После публикации проверяется окончательный кандидат. Мерж требует актуальных прав пользователя, GitHub App и выполненных правил репозитория.
8. GitHub merge API получает ожидаемый head SHA. Защита target должна требовать актуальную ветку и проверку именно нашего приложения; обход этих правил запрещён. Проверка target перед API-вызовом без серверной защиты оставляет гонку и не считается гарантией.
9. Автомерж по умолчанию выключен. Пока target не защищён от мержа непроверенного кандидата, автомерж недоступен. Ручной режим использует тот же допуск и не является обходом порога.
10. После неоднозначного результата публикации/мержа оркестратор сверяет GitHub-состояние по сохранённым идентификаторам. Повтор доставки Celery не означает повтор внешней операции.

## 6. Минимальная безопасность для всех зон

- **Приложение:** HTTPS, серверные сессии, безопасные cookie, OAuth state, CSRF, проверка владельца каждой операции/артефакта; квоты пользователей и глобальная очередь. До готового входа публичные дорогостоящие операции не открываются анонимно.
- **LLM:** provider keys только в конфигурации; никакого command execution/function calling. Репозиторий, требования и ошибки — данные, а не инструкции сервису. Не логировать prompts, исходники, ответы и ключи; usage неизвестен, если его нет в ответе.
- **GitHub:** минимальные permissions, разделение App JWT/installation token/user token. Действия от имени пользователя используют его разрешения; установка приложения не даёт любому посетителю право записи. Токены не передаются в браузер, sandbox и логи.
- **Webhook:** HMAC-SHA256 исходных bytes тела, constant-time сравнение, проверка до JSON-обработки; фильтрация поддерживаемых событий и дедупликация доставок. Потерянный webhook не отменяет повторной проверки SHA/прав перед записью.
- **Runner:** непривилегированный процесс, отсутствие сети/секретов/socket, минимальные capabilities, запрет повышения привилегий, ограниченные writable-каталоги и CPU/RAM/PID/диск/время. Установка зависимостей и collect-only тоже могут исполнять код.
- **Вход/выход:** ограничения размера, распаковки и времени; безопасные относительные пути; экранирование текста/логов в интерфейсе. Экспортер не открывает произвольные пути из ответа модели.
- **Качество:** LLM не может изменять прикладной код, существующие тесты, pytest/coverage-конфигурацию, добавлять исключения покрытия ради порога. Исполнение недоверенного кода и его отчёт не являются доказательством безопасности.
- **Секреты/эксплуатация:** внешние `.env`/переменные и закрытое хранение private key; шифрование пользовательских токенов с ключом отдельно от БД, очистка артефактов, восстановление после сбоя и ограничение расхода API.

## 7. Порядок командной интеграции

| Этап | Параллельная работа | Проверяемый результат |
|---|---|---|
| I0 — контракты и каркасы | Артём З: модели/API/очередь; Иван: вход/DTO; Вадим: LLM; Артём Х: экраны на fixtures; Макс: CI/Compose/runner | Общие примеры DTO, локальные проверки, различимые fake/real результаты; ни один модуль не ждёт готового GitHub для unit-тестов |
| I1 — вертикаль без GitHub | Upload либо подготовленный SourceSnapshot → контекст → LLM → шлюз → sandbox → отчёт → UI | Реальный LLM и реальный runner соединены; результаты/ошибки сохранены и видны; чужой код не исполняется в API/worker |
| I2 — устойчивое ядро | Default, lazy на заранее сохранённом diff, одна доработка, отказ/квота/таймаут, демонстрационный дефект | На исправном примере тесты проходят и покрытие ≥90%; в default выявлен заданный дефект; ошибки не дают ложный успех. Проверка не зависит от GitHub App |
| I3 — GitHub read | Вадим делает App/клиент, Артём З подключает HTTP/хранение, Артём Х — UI, Макс — URL/секреты | Вход, выбор публичного репозитория и веток, снимок по SHA; существующее ядро получает тот же контракт |
| I4 — GitHub write | Ветка тестов/PR, окончательная проверка кандидата, required checks, ручной мерж | Запись в отдельном демо-репозитории, отказ по stale/правам/порогам, отсутствие дублей |
| I5 — защита демо | Опциональный автомерж, общие негативные сценарии, полный Compose-запуск и документация | Целевой пользовательский сценарий воспроизводится по инструкции; ограничения явно показаны |

GitHub App планирует реализовать Вадим после основной LLM-части. При необходимости он передаст эту работу другому участнику.

Клиент можно разрабатывать по согласованным интерфейсам с mock HTTP, не дожидаясь готовности всех соседних модулей. Реальные публикацию и мерж проверяем в выделенном демо-репозитории после подключения сессий, проверки прав, хранения токенов/операций и допуска к мержу с учётом branch rules.

## 8. Приёмка общего продукта

- **Вадим + Иван:** сценарии соответствуют явным требованиям; lazy имеет маркировку inferred; ошибочный код не объявляется верным только из-за coverage.
- **Артём З + Макс:** известные покрытые/непокрытые строки дают правильный процент; отсутствие отчёта, пустой сбор, таймаут и нулевой знаменатель не превращаются в успех. Повтор задачи не дублирует внешнюю операцию.
- **Артём Х + Артём З:** после обновления страницы видны сохранённые результаты; нет чужих прогонов; UI показывает квоту, ошибку окружения, stale и причины запрета мержа.
- **Иван + Макс:** текстовый документ более 50 страниц принимается в фоне; ошибочный файл/слишком большой архив обрабатывается ограниченно; экспорт не выходит за выделенный каталог.
- **Вадим GitHub + Артём З:** тестируются потеря прав, удаление установки, повтор webhook, неверная подпись, смена source/target SHA, неизвестный итог мержа и повтор нажатия. Проверяются ручной режим и отдельно явное включение автомержа.
- **Макс + вся команда:** запуск на чисто подготовленном VPS по одной инструкции; health/readiness, HTTPS, конфигурация и cleanup работают. Результат fake/offline никогда не выдаётся за живой прогон.

## 9. Предположения и открытые решения

**ASSUMPTION T3:** начальная калибровка LLM — 120 секунд на этап, до 60 секунд на запрос, максимум три транспортные попытки в общем deadline; вход до 24 000 токенов, выход до 8 000; начальные тесты плюс две доработки. Это собственные ограничения приложения, не квоты провайдера. Не должно быть умножения retries на слоях SDK/worker/адаптера.

**ASSUMPTION T4:** PDF текстовый, OCR не входит; при N/A ручной мерж через сервис также заблокирован до отдельного решения. Дополнительные patch-pins, формы DTO и пути API уточняются владельцами. Утверждённый порог ≥90% при ненулевом знаменателе не является предположением.

| Что решить/проверить | Владелец результата |
|---|---|
| Доступная Gemini-модель, реальные квоты и качество; корректировка LLM-лимитов | Вадим |
| Репозитории/коммиты демо, эталонные требования, профиль зависимостей | Иван + Вадим; поддержку профиля подтверждает Макс |
| VPS/регион/домен, бюджет, Engine/runsc, ресурсы sandbox, размеры файлов, параллельность и хранение | Макс; прикладные ограничения согласует Артём З |
| DTO/OpenAPI, форматы feedback и отчётов, даты готовности стыков | Артём З с каждым производителем/потребителем |
| App permissions, callback/webhook, защита веток, HTTP-клиент и его pins | Вадим + Артём З/Макс по своим зонам |
